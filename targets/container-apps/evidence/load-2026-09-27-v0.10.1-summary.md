# Live Demo load runs on v0.10.1, 2026-09-27

Simulated player traffic against the Live Demo Environment running Release Tag `v0.10.1`
(Web `sha256:234cc6b4a30e0e782bd9fa04ee42a1d3eea37f70b348fbb90ca9d91373de3a97`,
API `sha256:7af9f4bda594f2426b72ef6a0f21f3b6020668f95dd94eb756ed32a17f3063fd`),
the capacity release: one room read per publish, a revision-aware forwarder, and a
fixed-cadence due sweep. The setup matches the [`v0.10.0` runs](load-2026-09-27-summary.md):
one API replica limited to 0.26 cores, Redis `maxmemory` 180 MB, traffic from a separate
Linux host, and API `runtime_summary` lines from two approved Container Apps log sessions
started five minutes apart and deduplicated. The harness started only after the first
summary arrived.

## Runs

| Run | Ramp (rooms) | Result | Client errors | Invariants |
|---|---|---|---|---|
| [registered](load-2026-09-27-v0.10.1-registered.md) | 1, 2, 5, 10, then Design Load | Completed; Design Load verdict `pass` | 0 / 3,625 | 6 pass over 80 matches |
| [probe](load-2026-09-27-v0.10.1-probe.md) | 6, 8, 10, 12, 14, 16 (`--ramp`) | Completed; no capacity knee | 0 / 7,485 | 5 pass over 170 matches |

The registered ramp stops at ten rooms instead of the pre-registered 15: on `v0.10.0` the
15-room step exceeded capacity before the Design Load step, so the harness dropped it
(Product PR #139). Everything else in the registered run is unchanged.

## Design Load

Ten rooms of four Human Participants at normal difficulty held a step p95 tick lateness of
101 ms with a median API CPU of 21.5% of the limit, so the Design Load holds and the
pre-registered fan-out rule is not triggered. Every one of the run's 65 summary windows
stayed at or below 102 ms.

Caveat: the harness starts all ten Design Load rooms together after draining the ramp,
so the step begins with a lockstep start rather than staggered arrivals.

- Probe 1 had 10 of 72 windows above 150 ms, 7 of them at 16 rooms. The `v0.10.1` probe had
  none of 75, and its worst window was 103 ms, at the 100 ms due-sweep cadence.
- Peak API CPU at 16 rooms fell from 0.19 to 0.11 cores (73% to 41% of the limit).
- Redis used at most 1.4% of `maxmemory` in both probes.
- Redis `WATCH` retries per window did not fall: up to 77 at 16 rooms on `v0.10.0`, up to
  103 on `v0.10.1`. Retries cost no visible lateness at this load.
- Sixteen rooms (about 78 sockets) is the highest load measured, not a ceiling: no step
  crossed 150 ms, so the new capacity knee lies above this probe.

## Caveats

- `at` in each result's `runtimeSummary` is when the harness received the line; the API
  emitted summaries on a steady 15 s cadence. Window-to-step assignment uses that time.
- The per-step stale column in both runs' step tables reads 0 because the harness credited
  stale frames to a field that was never set (fixed in Product PR #140). The run-wide
  stale-frame counts in the invariant rows (1,261 and 2,503) are correct.
- Rooms in the probe and the ramp mix 2 to 6 humans, 4 to 8 seats, and all difficulties.
- No room creation was refused by the hourly per-address budget.
